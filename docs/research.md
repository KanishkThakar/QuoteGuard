# Topic 6 research answers

A cache hit means a valid stored value exists under the exact lookup key. A miss means that value is absent, expired or unusable, so the application must obtain the result again. Miss counts do not equal upstream calls: a waiter can miss initially and then find the result produced by another worker. Cache Lab records both.

TTL is the maximum time Redis retains a key without another write. Latest ECB reference rates have a one-hour TTL because rates update daily but newly published values should become visible without indefinitely retaining the earlier observation. Historical rates use seven days: historical observations change less often, but corrections are possible. Draft calculations use fifteen minutes. An expiry is a miss, not a guarantee that the upstream source has changed.

Invalidation is hard because inputs and their dependencies change at different times. A cost update, fee change and rate refresh can race with an in-flight calculation. Deleting a key alone is insufficient: an older worker could refill it after deletion. QuoteGuard includes the input version, rate version and input hash in each calculation key. Transactional updates increment the quote version before commit; after-commit audit events publish the cause. Old workers can only address old keys and conditional database updates stop them from replacing current last-calculation results. Orphaned keys expire naturally; no broad flush is used.

Django per-view caching stores an HTTP response for a view. It is convenient for public, mostly identical pages, but an authenticated quotation depends on ownership, session/CSRF behaviour and several pricing dependencies. Accidentally caching a user-specific response under an incomplete key can disclose data. Low-level caching stores a chosen value under an explicit key, allowing precise versions and invalidation. QuoteGuard uses the redis-py low-level client rather than per-view response caching, so calculations and reference rates can be cached independently, and finalised snapshots remain database records.

Distributed locking prevents many simultaneous misses from fetching the same pair. The lock uses SET NX with a six-second expiry, a 1.5-second acquisition deadline and ownership-checked Lua release. The four-second upstream timeout is shorter than the lock lease. A waiter rechecks the result after acquiring the lock. Locks have a finite lease: a worker suspended longer than its lease cannot promise perfect exclusivity. Cache failure allows a bounded direct upstream attempt rather than inventing data. It does not provide stale fallback. Production scale may require an upstream circuit breaker and distributed rate limits.

Useful primary references: [Django cache framework](https://docs.djangoproject.com/en/5.2/topics/cache/), [Redis locking guidance](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/), [Frankfurter v2](https://frankfurter.dev/).
